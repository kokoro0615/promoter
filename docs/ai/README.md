## 2. 安全な取得

既存の作業ディレクトリ、未コミット変更、他のブランチを上書きしない。新しいディレクトリで始める場合の例:

```bash
git clone --branch docs/swe2max-jp-completion-20260919 https://github.com/kokoro0615/promoter.git promoter-swe2max
cd promoter-swe2max
git status --short
```

`promoter-swe2max` が既に存在する場合は別名を使う。既存チェックアウトを使う場合は、まずGit statusとローカル差分を確認し、fetchした文書ブランチまたはマージ済みmainから本パッケージを取得する。`reset --hard`、`clean -fd`、force pushで作業を消さない。

実装開始時に最新mainとの差分を調べ、文書作成後のコード変更を保全して統合する。文書に記載された過去のSHAへ実装を巻き戻さない。文書ブランチを元に実装用の別ブランチを作るか、文書がマージ済みなら最新mainから実装ブランチを作る。

## 3. Devin CLIとモデルの確認

Devin CLIがインストール済み・認証済みの環境で以下を確認する。

```bash
devin --version
devin models list
devin --help
```

公式資料では、`devin models list` はアカウントで利用可能なモデルを表示し、`/model` は対話中のモデル選択に使用する。`--model`、`--prompt-file`、`--continue` も公式コマンド一覧で確認できる。利用中のCLIに対応するか、実際のhelpも確認する。

- モデル: https://docs.devin.ai/cli/models
- コマンド: https://docs.devin.ai/cli/reference/commands

ユーザー指定はSWE-2max。ただし実際のモデルID、利用権限、max設定の表記を推測しない。`swe` は最新ファミリーを指すエイリアスであり、指定モデルと常に同一とは限らない。利用できないモデルを使用したと報告せず、実際のモデル名と設定を作業記録へ残す。

### 方法A: ファイルを指定して開始

一覧で確認した実IDに置き換えて実行する。

```bash
devin --model "<一覧で確認したSWE-2maxの実ID>" --prompt-file docs/ai/SWE2MAX_MASTER_PROMPT.md
```

山括弧部分は入力例であり、そのまま使うモデルIDではない。maxがモデル名ではなく推論レベルとして提供される構成では、公式に対応する設定方法を確認する。未確認のフラグを作らない。

### 方法B: 対話画面で選択して開始

```bash
devin
```

先に `/model` で指定モデルを選び、利用できる推論設定を確認した後、次を送信する。


## 4. 中断後の再開

同じディレクトリの直近セッションを継続する例:

```bash
devin --continue
```

別セッションから始める場合は `RESUME_PROMPT.md` を使用する。会話が残っていてもGit差分と実ファイルの再確認を省略しない。記録にない試験を実行済みとみなさない。

## 5. 外部ステージング確認で必要になる準備

実装開始時に全設定が揃っていなくても、設計、業務機能、UI、実DB試験、連携アダプター、契約試験は進められる。ただし最終的な外部ステージング合格には、対象アカウントの所有者が用意する権限や承認が必要となる。

| 用途 | 最終確認時に必要なもの |
|---|---|
| 決済/利用料 | Stripeの許可されたテスト環境、テスト接続店舗、Checkout/Connect/Billing/Webhook設定。 |
| 個人認証 | LINE Loginのテストチャネル、テスター、callback設定。 |
| メール/LINE通知 | SESの許可された送信元/テスト宛先、LINE Official Accountの許可されたテスト送信先。 |
| POS/会計 | Square Sandbox、freeeの開発用テスト事業所とOAuth。 |
| ステージング | 許可されたクラウド環境、DB/ストレージ/HTTPS/実行ロール、必要な費用承認。 |
| Web Push | ステージングoriginと対象ブラウザ、鍵の安全な設定。 |

既に利用できる接続・設定は先に調べる。秘密値はチャットや公開GitHubへ貼らず、環境変数、Secrets Manager、GitHub Environment secrets等の許可された経路へ設定する。キー名・設定場所・未設定という状態だけを文書へ残す。

サービス契約、加盟店審査回答、有料資源の新規契約や増額を、設計選定の委任だけで実行してはならない。予算未定のため、AWS構成はまず設計・費用試算・IaCのplanを作り、承認済み環境または明示承認された費用の範囲だけ実リソースへ適用する。
