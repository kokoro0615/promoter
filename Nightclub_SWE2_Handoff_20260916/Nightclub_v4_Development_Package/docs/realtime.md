# 同期・通知・PWA・障害時運用 v4

**設計案／Confidence：Medium。目標値は未達成。**

## 1. 正本と配信

DB更新とOutboxを同一取引へ保存する。[T14] 配送は少なくとも1回の想定で重複する。通知送信の成否は業務状態を戻さない。受信端末はaggregate_id/versionで古い情報の上書きを防ぐ。通知を見なくても一覧検索が最新条件を取得できる。

## 2. コミット順序と取りこぼし防止

sequence採番とcommit順は同一とは限らない。[T05] v4参照方式ではevent_stream_headsを当該営業の書込開始時にロックし、last_seqを通常行として増やし、outboxと同じ取引でcommitする。rollbackなら番号も戻る。last_seq=101が見えるのに未commitの100が後から現れる設計を避ける。1店舗10名程度の想定負荷で許容されるかを実測し、大規模時はCDC等へ変更管理する。

snapshotはREPEATABLE READ等の一貫した読み取りでcursorと全データを同じDBスナップショットから取得する。ページング時は短期スナップショット成果物を維持し、各ページを別々の最新SELECTにしない。全ページ適用後にsnapshot_tokenとcursorを受領し、それ以降のchangesを取得する。保持期限切れは410相当のRESET_REQUIREDで全取得へ。

ロールや他者情報を含むraw outboxをブラウザへ出さない。changesは現在の権限で射影し、権限外のイベントを除いた範囲をカーソルが進む場合も、カーソルの対象範囲・件数で顧客情報を漏らさない。停止後の購読は再認可して閉じる。

## 3. 入口の反映確認

受領ACKは「対象snapshot/changesを画面の参照データへ適用した」状態。人の既読ではない。稼働入口一覧はdevice/operator/eventの組。ACKのcursorは配布済みtokenと一致し、将来番号の任意送信は拒否する。これは正しいクライアント実装の運用証跡であり、物理的に人が画面を見た証明ではない。

入口2台のうち1台だけ反映なら「2台中1台」。紹介者自身のスマホACKを入口ACKにしない。背景化・画面消灯・担当者終了では非稼働またはSTALEを明示し、同期率の分母から無記録に消さない。

## 4. 目標と補助

正常オンライン・前面表示で保存から適用ACKまでp95≤2秒、p99≤5秒をv3から継承。検索p95≤1秒、入場API p95≤1.5秒。外部決済待ち、人の本人確認、金銭授受は別計測。未受領・タイムアウトを遅延集計から除外しない。

Realtime adapterで通知しchangesを取得。切断時は前面表示中のみ短周期pollへ切替える案。周期・負荷は実測する。ブラウザ復帰時は必ず再同期。PWAの通知、音、バッジは補助であり成立条件ではない。[T10][T11]

## 5. 通信断の境界

一部端末不調は正常端末へ引継ぎ。外部回線断は予備回線、復旧しなければ責任者が単一受付へ集約。事前同期済みの当日最小リストを検索し、必要時に暫定入場のローカル操作を別台帳へ記録する。[T18]

新規フリー承認・料金変更・返金・通常入場確定をオフラインで自動成功にしない。完全切断した複数端末の重複防止は保証しない。回復時は暫定記録をimportして照合し、二重・取消済み・枠超過を責任者が解決。現実の入場を消して整合したように見せない。

## 6. キャッシュと更新

当日データは営業終了後12時間以内の削除を初期案とする。個人スマホへ他者台帳を恒久保存しない。IndexedDBにsecret、PIN、カード情報は置かない。OSによるストレージ回収やユーザー削除があり得るため、キャッシュだけを唯一の正本にしない。[T18]

Service Workerの更新は営業中に強制reloadしない。未送信入力の確認、旧API版の互換期間、schema version、キャッシュ移行・破棄、rollbackを試験する。背景で常時同期し続ける前提は置かない。
