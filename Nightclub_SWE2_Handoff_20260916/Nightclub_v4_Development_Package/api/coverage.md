# API契約の範囲と未確定境界

**区分：開発用契約案／Confidence：Medium。** openapi.yamlはR1の主要業務コマンドと読み取り動線。DBテーブルの全CRUDを自動公開する契約ではない。APIサーバーは未実装。

## 契約化した中心領域

個人セッション、入口端末登録と担当者切替、顧客名検索、常連指定、個人許可、営業ポリシー下書き・プレビュー・公開、ゲストと条件内訳、通常／入口承認、本人照合、部分入場、取消・訂正・再入場、同期snapshot/changes/ack、VIP予約・移動・決済・返金、基本会計・締め・帳票、管理設定の作成を定義する。

## 専用設計が必要な境界（スコープ削除ではない）

OIDC callback・代替メール認証・管理者追加認証は採用認証基盤に合わせて確定する。PSP署名ヘッダーとWebhook payloadはPSP決定後のアダプター仕様、POS/API/CSVは対象製品の実サンプルで確定する。通知チャネル4種の送信契約はプロバイダー選定に依存する。

管理機能の全編集・一括・エクスポート形式の詳細、予約の全ポリシー組合せ、R2契約・R3商品在庫・R4高度分析は本体143機能とバックログに残し、対象スプリント開始前にAPI補完する。主要契約があることを全143機能の全エンドポイント確定とはしない。

## 契約変更ゲート

各バックログ項目に必要な画面、API、権限、DTO、エラー、DB、受入テストを紐付ける。未定のproviderはUNDECIDEDとして公開しない。金銭・権限・受付のコア型を変更した場合はconsumerとschemaの回帰を行う。

## 共通規約

Cookie認証の書込はCSRF/Origin検証。入口ではX-Operator-Contextが必須で、cookieと現在担当に一致。404と403の使い分けは権限外リソースの存在漏えいを避ける。記載例のexample.invalidは接続先ではない。

409は版・確定・枠の競合、422は業務条件不成立、429は試行制限、503は未確定を成功に見せず再照会を促す。エラーはRFC9457の形にcode/trace_idを加える。[T19]
