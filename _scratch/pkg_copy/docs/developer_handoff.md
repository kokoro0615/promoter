# 開発引継ぎ・完了の定義

最初にREADME、requirements_v4、planningの台帳、architectureを読む。次に参照モデル→API→取引→試験の順で縦の業務を確認する。旧v3はbaselineに固定し、入口を「承認不可」「不在時のみ」に戻さない。

## 最初の実装単位

1. 店舗と個人所属・共用端末・担当者セッション。
2. 当日営業と可変料金・常連許可の設定。
3. 名前検索→ゲスト追加→省略／入口通常承認→一覧同期。
4. 顧客照合→部分入場→紹介者別実績。
5. VIP予約→事前決済→在庫とWebhook照合→基本精算。

アプリのコードを生成・実装する際も、ロール名や画面表示だけで認可せず、定義したトランザクションを守る。adminのRLS無効化を便利な初期実装として残さない。デモ用の固定無料枠を本番ルールにしない。

## Definition of Ready

対象要件ID、採用／提案の状態、スコープ、画面DTO、API contract、DB制約、認可、エラー、再送、監査、受入ケース、担当と依存が決まっている。PSP等の未選定をモックで置く場合は実運用不可のfeature gateを付ける。

## Definition of Done

コードレビュー、静的検査、単体、API契約、DB/RLS/並列、E2E、端末・ネットワーク、金銭照合、監視・復旧、ドキュメント・追跡表の更新。未実施は未実施。テストデータ以外の顧客情報をソース管理へ入れない。

## 本番判定

料金・枠・常連名簿・担当者・端末・決済条件の初期設定が済み、R1対象AT/AT4が合格し、未解決の重大欠陥がないこと。決済・返金・権限・入場・復元の不具合は件数が少なくても公開不可。

設計ファイルの静的整合性がPASSであっても、アプリ動作・負荷・売上改善を保証しない。差別化は限定営業で確認往復数と精算工数を実測する。
