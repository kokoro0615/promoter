# 技術構成・ADR v4

**区分：設計案／Confidence：Medium。** 業務確定事項はrequirements_v4.md。クラウド製品・料金・契約は未選定。ここで新しい本番環境を作成したものではない。

## 1. 構成と責任

個人PWAと入口共用PWAは、同じバックエンドの業務データを使う。ブラウザから「承認済み」や「売上」を直接DBへ書かせない。APIは本人／端末／担当者を解決し、コマンドハンドラーへ渡す。ハンドラーが認可、設定判定、ロック、台帳、監査、Outboxを一つの取引にする。[T03][T04][T07][T14]

推奨は、R1をモジュール分割した単一アプリ（認証、顧客、許可、受付、VIP、会計、通知、帳票）として実装する方式。DBはPostgreSQLを参照設計とする。言語案はTypeScript。これらは業務上の確定事項ではなく、技術責任者の設計審査で採択する。

|層|役割|行わないこと|
|---|---|---|
|PWA|入力、名前候補、承認・入場、同期適用、最小キャッシュ|自分で権限・料金・支払済みを確定しない|
|BFF/API|cookie検証、CSRF、最小データ射影、入力契約|任意actor_idやtenant_idを認可済みとして信用しない|
|Domain commands|同時操作、条件・枠・支払、監査、Outbox|ロック中に決済事業者へネットワーク要求しない|
|PostgreSQL|正本、複合FK、ユニーク、範囲排他、台帳|業務横断制約をJSON任せにしない|
|Worker|Outbox配信、通知、決済照合、帳票、期限処理|重複配送で二重請求・二重入場させない|
|Realtime adapter|認可された更新通知・再接続|配送成功を人間の既読としない|
|PSP/POS adapters|契約済みの決済・会計の境界|他店舗のmerchantに流用しない|

## 2. ADR決定表

|ADR|選択A|選択B|推奨・判断条件|
|---|---|---|---|
|ADR-01 同時更新|単一DB＋短い取引|独立マイクロサービス|R1はA。会計・枠の整合を優先。Bは負荷と組織分割が実証された後|
|ADR-02 クライアントDB接続|API経由の書込|BaaSへ直接書込|R1コマンドはA。Bの利用時も同じ原子的コマンド・RLS・本人識別が必要|
|ADR-03 リアルタイム|管理Realtime／常設gateway＋変更API|短周期poll中心|Aを推奨、Bは障害時補助。実プロバイダは接続・費用・夜間運用で確定|
|ADR-04 入口認証|登録端末＋個人PIN|担当者ごとに毎回LINE|初期案A。端末と担当者の二重検証が条件。Bは初回個人登録と管理画面向け|
|ADR-05 入口承認|承認→同一画面で入場|承認と入場の複合API|初期A。部分成功の理解が容易。Bは追加検収後のみ|
|ADR-06 テナント|共有DB＋厳格な境界|会社ごと別DB|初期A参照。特殊な契約でBを再検討|

BaaSやVercel等の存在・接続・採用を前提にしない。HTTPホスティングが常設WebSocketや長時間workerを提供するかは選定時に確認し、未確認のFunctionに常駐処理を置かない。

## 3. 開発ゲート

G0で要件IDと範囲・責任を合意。G1で端末と画面をレビュー。G2で認証→登録→許可→承認→同期→入場の縦の処理を完成。G3でVIP・決済・返金・照合・復元。G4で限定4営業。G5で全員運用。VIP事前決済をR1から削除しない。

## 4. 契約の正本

業務条件は本体、APIはOpenAPI、DB構造はmodel.json、設定の形はJSON Schema、横断ルールはtransactions.md。矛盾が見つかった場合は「どれかを都合よく採用」せず変更台帳に記録し、関連テストを更新する。
