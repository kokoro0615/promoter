# 画面・権限・操作・表示仕様 v4

**採用した動線／Confidence：High。画面寸法・操作詳細／Confidence：Medium（実機未検証）。**

## 1. 共通ルール

文字・状態名・人数・金額を併記し、色だけで判断させない。スマホ縦画面で主要操作に横スクロール不要。44 CSS px以上を操作領域の設計目標として継承。日本語・英語の基本UIをR1から提供。名前検索中心なのでQR起動を初期画面に固定しない。

## 2. UI-05の主画面（構造例）

```text
店舗名 ／ 営業名      担当：スタッフB [交代] [ロック]
入口端末：Gate-01    同期：最新 00:42:18
[ 名前・読み・紹介者で検索                           ]
[受付可能] [承認待ち 3] [入場済み] [要確認]

ヤマダ様 3名       紹介者：DJ A
フリー 1名／割引2名  本人照合：未確認
入場済み 0名／残り3名
[詳細・照合・判断]
```

右側または下部の詳細パネルで操作を完結。同期更新で検索文字や人数選択を消さず、対象条件に変更が来た場合だけ差分を提示する。氏名が同じ2人を1行にまとめない。

## 3. 連続操作の分岐

受付可能→本人照合が必要なら確認→支払の記録／確認→条件別の今回人数→入場確定。承認待ち→その場で通常承認→同じ詳細内に入場操作を表示。承認のみ成功して入場が失敗した場合は「承認済み・未入場」と表示する。

「承認」と「入場」の2操作は別処理だが、別画面へ移動・再検索・同じ名前の再入力をさせない。誤操作防止の確認は対象人数・料金を明示し、毎回長文の警告を読ませる方式にしない。

## 4. 共用端末の交代

常時担当者名を表示。交代で前担当の入力下書きが残っていたら保存せず破棄／戻るを選ぶ。新担当へ過去の金銭操作や他者の顧客メモをそのまま引き継がない。古い別タブはロックし、書込時にもoperator contextを照合する。

## 5. エラー表示

NAME_AMBIGUOUSは本人確認不能ではなく候補が複数であること。OPERATOR_CHANGEDは再ログインを促し、勝手に新担当へ操作を付け替えない。ALREADY_DECIDEDは誰がどう判断したか権限内で表示。QUOTA_EXCEEDEDは上限変更ボタンを入口へ安易に見せない。PAYMENT_UNCONFIRMEDではお客様が未払いと断定せず、再照会・店舗確認へ。

## 6. 計測

登録時間は入力開始→保存成功、受付UI時間は検索選択後→入場成功。人の本人確認と金銭授受を別記録。画面速度が早いだけで待ち行列が短くなったと断定しない。実測は匿名化したtrace IDで実施する。
