# VIP・会計・紹介者帰属・報酬 v4

**継承要件／設計案：Confidence Medium。金額例は仮定。税・契約条件の適否は未確認。**

## 1. R1境界

VIPテーブル予約・事前決済・返金・2Dフロア・基本精算は初期対象。一般入場のオンライン事前販売、商品在庫・POS全体はR3へ継承。入口の現金／外部端末の受領記録はR1。PSP・契約主体は未確定で、実決済開始を無条件に許可しない。

## 2. VIP在庫と予約承認

物理テーブルIDはフロア配置版から独立し、配置変更で予約を消さない。table_allocationsの占有時間は準備・清掃を含み[start,end)。同じ物理テーブルは別イベントでも重複占有不可。[T17] 結合は各物理テーブルを個別引当し、移動は全対象を取引で切替える。

時間が過ぎたHOLDは自動的にDB排他条件から消えない。期限ジョブと予約コマンドが期限を確認しRELEASEDへ変更する。期限後にPSPの成功が来たら、他の確定予約を追い出さずPAYMENT_EXCEPTIONへ。空き再確保、顧客への代替案、返金のいずれかを権限者が判断する。

予約の手動承認はbooking_decisions。入場フリーの承認はapproval_decisions。VIP予約が確定しても入場料別なら別の入場条件を確認する。入場料込みなら同じ料金を二度請求しない。

## 3. 利用額・入金・預りの分離

sales_linesは実際に確定した利用明細。paymentsは入金、payment_allocationsは会計・明細への充当、refundsは返金。預り金の入金だけでsales_lineを作らない。PSP手数料は費用・照合項目であり顧客利用額から勝手に消さない。

例1：有料2名×2,000円＝入場利用額4,000円。現金4,000円を受領し、初回入場に対応する売上行と充当を関連付ける。同じ操作再送で行を増やさない。

例2：VIP預り20,000円、最終利用80,000円、当日60,000円。利用額80,000円、入金計80,000円。20,000円を再加算して100,000円としない。6人に80,000円ずつ帰属もしない。

例3：支払済み40,000円から10,000円返金指示が処理中。利用可能資金は返金予約分を差し引く。返金失敗時だけ予約を解放。利用取消が必要なら元売上行へのCREDIT行を別記録し、返金と売上取消を同義にしない。

## 4. 部分入場と支払

paymentsの成功残高−返金予約−有効充当をロック下で検証。入場コマンドが今回の選択人数に対する売上行（source_key=入場操作＋内訳）を生成し、対応額をpayment_allocationsへ記録してから入場を確定する。先に全員分の入金があるなら残額を次の部分入場で消費できる。

VIP預りを無断で通常入場へ流用しない。会計のkindとbooking・visitを一致させる。客が店内で使った金額がPOS等と紐付かない場合は未計測であり0円ではない。現金・外部端末の店舗確認とPSP照合済みの状態も区別する。

## 5. 紹介者と報酬

来店ごとにreferrerを保持。作成者、承認者、入口担当は別。R1の主紹介者は1名。協力者のメモを売上配分と混同しない。多者配分を有効化する場合は明細ごと10000bpを同じ確定版で検証する。

報酬はreward_rulesの契約版で計算。第一回有料入場14名×500円＝7,000円はテスト例。フリーやVIP率、税・丸め・返金・支払日は設定／契約が必要。未設定を0円報酬として確定せず、規則未設定と表示する。

入場・会計・規則版・除外理由・調整までsettlement_linesで追跡。締め後はreward_adjustmentsで調整。settlement_paymentsは銀行等で別途実行した支払の記録であり、送金機能ではない。

## 6. PSP共通境界

生bodyによる署名検証、merchant・金額・通貨・予約照合、外部event ID重複排除、順序逆転の再照会、冪等な請求・返金を実装する。[T12][T13] ブラウザ成功URLやクライアントのpaid=trueを正本にしない。PSP選定前のwebhook adapterは有効化しない。
